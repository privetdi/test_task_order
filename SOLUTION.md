# Решение

## Что сделано

Добавлены `gross`, `discount`, `net`; `total` сохранён равным `gross`. Суммы хранятся и суммируются в целых копейках, в ответе переводятся в рубли. Учитываются только оплаченные заказы, пустые дни возвращаются с нулями.

Миграция добавляет фактически оплаченную сумму и заполняет её для старых заказов исходной суммой. Применение версии заказа выполняется в транзакции с advisory lock по идентификатору: конкурентные вебхуки и синхронизация не перезаписывают новую версию старой. Сигнатура `createContainer(db, api)` и интерфейс `OrdersApi` сохранены.

## Причина расхождений

Исходный код вычислял смещение таймзоны на текущую дату и применял его ко всем историческим заказам. У клиента `c_7` таймзона `Europe/Berlin`: 29 марта 2026 года UTC+1 меняется на UTC+2. Из-за этого часть заказов около полуночи попадала в соседний день.

Причина найдена при проверке расчёта локальной даты и подтверждена тестами переходов времени. Теперь дата каждого заказа определяется через `Intl.DateTimeFormat` в таймзоне клиента на момент `createdAt`. Результат не зависит от даты запуска отчёта.

## Наблюдения

- `Math.floor(rub * 100)` терял копейку, например для `1.15`. Перевод исправлен с использованием десятичного представления и BigInt.
- API отдаёт суммы строками, даты без зоны, 429 с `Retry-After` и без него, 200 с `error: rate_limited`, пустую финальную страницу с прежним курсором.
- Вебхуки повторяются и приходят одновременно и не по порядку; меняются статусы и скидки.
- Обновлены зависимости с известными уязвимостями. npm audit после обновления: 0 известных уязвимостей.

## Допущения

- `amountPaid` имеет приоритет над расчётом по `discountPercent`. Если оплата отсутствует, применяется процент; при отсутствии обоих полей скидка нулевая.
- Оплата каждого заказа округляется до ближайшей копейки, половина — вверх. Для исходной суммы сохранено отбрасывание долей копейки.
- Процент допустим от 0 до 100, оплата — от нуля до исходной суммы. Невалидный вебхук получает 400; синхронизация пропускает такой заказ и считает его невалидным.
- День определяется по `createdAt`, актуальная версия — по `updatedAt`; равная версия считается повтором. Используется закешированная таймзона клиента из API.

## Проверка

Использован Codex для анализа, реализации и проверки.

- `npm run typecheck` — без ошибок; 43 теста прошли на Node 20.20.0 и 24.22.2. Проверены скидки, округление, старые данные, переходы времени, конкурентные версии и повторы вебхуков.
- На новой БД выполнен полный сценарий ТЗ: синхронизация, вебхуки, запрос статистики. Получено 5030 заказов на 52 страницах, невалидных нет. Все 92 вебхука получили HTTP 200.
- `result.json` сохранён из ответа сервиса. Независимый расчёт по исходным заказам и копии вебхуков на Python с `Decimal` и `zoneinfo` совпал по всем пяти дням и суммам.

## При наличии времени

Добавил бы подпись вебхуков, авторизацию служебных маршрутов, ограничение периода отчёта, обновление кеша и хранение истории таймзоны клиента. Для больших объёмов перенёс бы агрегацию в PostgreSQL, проверки зависимостей — в CI.
